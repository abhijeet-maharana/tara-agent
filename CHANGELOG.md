# Changelog

## Unreleased

- **Silent runs keep their history; job option `quiet` removed.** A run that ends `[SILENT]` no longer removes anything: its streamed steps stay in the thread (finished as `🔇 Nothing to report · <duration · steps · model>`), the status line reads `🔇 <job> · <meta> · nothing to report`, and its session stays to ask about, also for queue and Run now threads. A learning note goes in that thread. `quiet` (unused by any job) is gone from the job schema, so a job with `"quiet": true` now fails validation; drop the key. `StreamReply.discard` removed.
- **Browsers page** (`/browsers`, 🌐 in the sidebar): each shared Chrome (host `browsers`) with its status and who uses it, and per project the logins its browser needs, written down in the new `.tara/logins.json` (service, account, note, sites, `public` hosts), with the jobs and chats that used each over the last 30 days, the often-opened sites no login covers, and the logins several projects share. For deciding which Chrome profile each project needs and what to sign in to. Sites come from browser tool calls with a `url` in the transcripts (read through sudo as the run user, cached per file until it changes). New `src/http/browser-usage.ts` (`SiteScanner`, `sitesIn`, `projectBrowser`, `projectNeeds`, `probeBrowser`, `loadLogins`), `src/http/browsers.ts`, `Store.sessionJobs`, `JobInfo.locks`.
- **Run messages use the job's name.** Scheduled triggers and the threads a run opens for itself say `Run <job name>` (`Run Weekly GA4 Audit`) instead of `Run <id>`; the id is used only when two jobs of a project share a name (`runName`). The bot finds the job by name (any case and spacing) or id (`findRunJob`), so earlier `Run <id>` messages still work. `parseScheduledRun` now returns the text after "Run".
- **Browser tabs are closed after every job that drives the shared Chrome.** A job holding the browser lock (`chrome`) has its tabs noted when it gets the lock; when it ends (any trigger, any outcome) the tabs it opened or moved to another page are closed before the lock is released, keeping one new-tab page so Chrome stays up. New host `browsers`: a list of Chrome instances (`lock`, `cdpUrl`, `closeTabs`; default one, `chrome` on `:9222`), so each identity can have its own Chrome profile and lock and only the browser whose lock a job holds is tidied. `src/runner/browser-tabs.ts`.
- **Streaming failures are logged.** When Slack refuses a live stream (at the start or mid-reply), or says the app can't stream at all, tara logs a warning with Slack's error code and the channel and thread, and says how the reply continues (plain messages without tool steps, or edited messages until restart). Before, the fallback was silent (`StreamPort.report`). A stream Slack seals on a long turn and that reopens is not logged.
- **`defaults` in `jobs.json`.** A file-level `defaults` object sets `harness`, `model`, `locks` or `timeoutMinutes` for every job that doesn't set its own (a job's `"locks": []` still opts out). Unknown keys are refused. It is merged into each job before validation, so errors still name the job (`jobsFileSchema`, new `jobDefaultsSchema`).
- **Scripts live in the skill too; `preScript` and `agent` are gone.** Every job runs the model, and its skill section's `### Before you start` part says which scripts to run (any number), with the old wake-gate rules (`{"wakeAgent": false}` or no output → `[SILENT]`). A script-only job becomes a skill that runs the script and posts what it printed. Claude's Bash timeout is set to the job's `timeoutMinutes` (`BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`). Runs may keep a useful script in the skill's `scripts/` folder (the job system prompt no longer says to only propose it), and learning turns may fix scripts in a skill folder or `.tara/scripts/` without a ⚠️ (`learnOverreach`). Removed: `runScript`, `parseWakeGate`, the `## Script Output` block and the dashboard's "Runs first" line; stored `script_output` still shows for older runs. `move-prompts` moves `preScript` / `agent` as well. A run's thread now opens with its status line straight away, also for `quiet` jobs (removed again when it ends `[SILENT]`).
- **A job's instructions live in its skill; `prompt` is gone from `jobs.json`.** The job's first skill holds a `## Job: <id>` section (steps: `### Step: <name>`, plus `### Every step`), and the run is told to follow it (`jobInstructions`, `stepInstructions`); learning turns improve it with the rest of the skill. `skills` is now required unless `agent: false`, a step may name its own `skill`, and `prompt` / `promptFile` are refused with a message saying where the text goes. **Breaking:** run `tara-agent move-prompts <repo> --write` to move existing prompts (`planPromptMove`); `import-hermes` does it for imported jobs.
- **`run <skill>` in Slack.** "run …" also matches the skills a job uses: an exact skill name starts the job using it (`run google-analytics`), a skill several jobs share offers them as buttons, and skill words count for partial matches. A job's own name or id still wins (`matchJob`, `JobRef.skills`).
- **Fixes.** `send_file` reads what it checked: the file is opened once (no final symlink, no FIFO wait), the open file is checked against the project and temp roots (Linux: `/proc/self/fd`), and the upload sends those bytes (`readChecked`; `ChatPort.uploadFile` now takes `{name, data}`). Before, a run could swap a folder for a symlink between the check and the read and have tara-agent upload a file only it can read, such as its own environment. A run whose CLI exited but left a process holding its output open (a browser, an MCP server) no longer hangs forever holding its thread, job slot and locks: 10 s after the exit the process group is killed and the pipes closed (`exitGraceMs`), and a timeout or stop signals the group even after the CLI itself is gone. A job paused between its trigger message and pickup is skipped instead of being started by the pickup watchdog.
- **A project channel holds only `Run <name>` messages.** Everything tara starts in a channel opens with a top-level `Run <name>` and puts the rest in its thread; `Run` messages are never edited (the status line is the thread's first reply, for scheduled runs too). Queue, Run now and `quiet` runs open their `Run <id>` thread only once they have something to post, and remove it when they end `[SILENT]`. The health digest is a `Run health-digest` thread, an invalid jobs file `Run jobs-reload`, Code-page questions `Run code-question`, voice tasks `Run voice-task`. Cards a project server raises (`POST /items`, `/items/ask`) go in one `Run <queue>` (questions: `Run <kind>`) thread per day instead of a channel message each (new `day_threads` table, `Approvals.dayThread`, `Store.setItemThread`); their outcome, revise and sending run follow in that thread. A learning note goes only in the run's thread (none when a silent run's thread was removed). New `openRunThread`.
- **Retention for the state database.** New host `retentionDays` (default 90, min 14): at start and daily, runs, slot claims and sessions not used for that long are deleted (`Store.prune`). Each job's latest run stays, so a rarely run job keeps its last result; approval cards are kept. A reply in a thread older than that starts a new session (Claude Code has deleted the old one by then: `cleanupPeriodDays`, 30 days by default).
- **Fix: run costs were counted again on every turn of a session.** The CLI's `total_cost_usd` is the session's running total and carries over `--resume`, so every chat turn, continued job and learning turn stored the whole session's cost (all 292 multi-run sessions on one host: $2,513 recorded, $690 real; learning turns looked like ~$4 each, really ~$0.09). `recordRun` now stores each run's share in `cost_usd` and the running total in the new `runs.session_cost_usd`; a migration converts stored history the same way. Every cost on the dashboard (Jobs usage, week totals) drops to what was really spent.
- **Scheduled trigger messages read `Run <id>`** (e.g. `Run content-stats-views-likes`) instead of `` ⏰ Scheduled: *<name>* (`<id>`) ``: the words a person would type; the run streams into its thread as before. `scheduledRunText(id)`. A top-level `Run <id>` starts the scheduled slot only while one is waiting for that job (`scheduledRun` returns whether it did); otherwise a person's message is a normal run request. The older form is still parsed.
- **Security fixes from a code review.** Tab and fallback proxy: a path like `/app/<name>//evil.host/x` no longer reaches another host, and the bearer token and `x-tara-admin`/`x-tara-run` headers are stripped (new `passThrough(req, res, base, path)`). Approvals: the dashboard sends the card's `updatedAt` as `seen` (`Decision.seen`, also per id in `/items/bulk`), and a card re-proposed since is refused with 409. Card media must be `http(s)` or `/` URLs (`safeMediaUrl`), checked on input and when rendered. New `crossSite`: cross-site writes (an `Origin` of another host) are refused, and a loopback-bound server answers only to loopback Host names, on HTTP and WebSocket. `tara-priv` resolves symlinks in path arguments, re-checks the pattern, and runs the resolved path. Model output's `<!channel>`/`<!here>`/`<!everyone>`/`<!subteam^…>` are posted as plain text (`defuseBroadcasts`).
- **Reliability fixes.** A chat turn takes its slot only after setup, so a setup error can't leak a chat slot; a learning turn that fails during setup can't leak a job slot. A job a person stopped is finished as `stopped`, not `aborted`, so a restart doesn't run it again. Queue `slots` and `tz` are validated when `queues.json` loads, and one broken queue no longer stops the others. `/internal/permission` takes bodies up to 5 MB and `/internal/approval` up to 200 KB (a large Write was silently denied).
- **Learning turns are checked.** Tool events carry the `file` an edit tool writes; a learning turn that edits a non-`.md` file or uses a shell or MCP tool gets a ⚠️ line in its Slack note (`learnOverreach`).
- **Self-improvement after every run.** `selfImprove` is now a mode: `"always"` (new default; `true` maps to it), `"trouble"` (the old behaviour) or `"off"` (`false`). In `always` mode every Claude job run and chat turn that used a tool gets one learning turn; a clean run is asked to look back for what it had to figure out (new clean-run `learnPrompt`), a run with trouble gets its reasons as before. Jobs can override the project with their own `selfImprove`. New `learnReasons`, `SelfImprove`.
- **Scheduled runs go through Slack.** At cron time (and for catch-up) the scheduler posts `` ⏰ Scheduled: *<job>* (`<id>`) `` in the project channel, and the bot, receiving its own message, starts the job in that message's thread. The trigger message is the run's status line (⏳ → ✅/❌ + headline), and the run streams into its thread. Runs that find nothing are no longer deleted: `[SILENT]` shows "🔇 nothing to report" and keeps the thread and session to ask about, and a pre-script gate skip says why on the message. The slot is still claimed in SQLite first and taken once (`Scheduler.trigger` with `SCHEDULE_BY`); a trigger message the bot never received leaves the slot claimed as `running`, so the next start catches it up, and a failed post marks it `aborted`. Slack gateway: `ignoreSelf: false`, `toIncoming` takes the bot id and passes our own top-level trigger messages as `fromSelf`, which skip `allowedUsers`. New `src/scheduler/slack-trigger.ts`; `JobTrigger` `schedule`/`catch-up` take an optional `thread`. Optional `SLACK_USER_TOKEN` (xoxp-…, user scope `chat:write`, now in the app manifest): trigger messages are posted as that person instead of the bot (`ChatPort.postAsUser`); such a message counts as theirs (`allowedUsers` applies) and still runs only a slot the scheduler posted. The token is stripped from the CLI's environment. A trigger the bot hasn't picked up in 2 minutes is started by the scheduler in its thread (`pickupTimeoutMs`). A top-level message that looks like a trigger but doesn't parse is dropped instead of going to Claude. New job option `quiet` (default `false`): no trigger message, gate first, nothing posted for a gate skip or `[SILENT]`, for monitors that run often.
- **Draft cards in Slack are one line.** A `slack` queue card with its own channel message now shows only its title and status there; the body, fields and checks are the first reply in its thread (new `items.detail_ts`, `Store.setItemDetail`), and a refresh edits both. Cards already posted are slimmed on their next refresh. Cards a run proposed still go whole in that run's thread.
- **Every job run streams live in its Slack thread.** Scheduled, catch-up, queue and continued (after a card decision) runs now stream their steps and text into the job message's thread, like runs started with `run <job name>`; they are addressed to whoever started or continued them in Slack, else the project `owner`. Without an `owner` scheduled runs keep the old status line + details. Script-only jobs (`agent: false`) post the result line in the channel and the script output in its thread instead of one channel message.
- **Jobs page: On demand tab.** The Jobs views are now **List · On demand · Timeline**. A job with no `cron` that no queue runs (`.tara/queues.json` executor) is listed on **On demand** (`/jobs?view=on-demand`) instead of List, with **Run now** as its one action (no Pause; **Resume** if disabled) and a search box. `/jobs#job-…` links to such a job forward there. Queue jobs stay folded under **Run by a queue** in List and name their queue ("none (executor of the content queue)"). Phones: the Jobs filter chips scroll sideways on one line each instead of wrapping, and a job card's buttons are full width and 40px tall. New `JobView.queues`, `JobsView`; `jobsPage` takes a `view`.
- **Send a note on a card without deciding it.** An approval card's note box (opened by **Note…**, or **Revise or note…** on a draft) has a **Send** button: the note shows in the card's Slack thread ("📝 Note from the Approvals page: …") and goes to Jarvis there as the owner's reply, told the card is still waiting, so it answers in the thread and changes or withdraws the card only if asked. The card keeps waiting. A note typed before picking an option still goes with that decision; Revise still asks for a new version. New `POST /items/<id>/note` `{text}` (unlocked browser on another device) and `Approvals.note`.
- **Code page**: a repo's changes are grouped by folder (its first two folders, e.g. `board/web`), each with its file count and lines; with more than 30 changes the folders start closed. A repo with uncommitted changes and a last commit over 3 days old shows "uncommitted · last commit 9d ago" in amber, on `/code` and its page, and Home's "Needs attention" lists it ("Job Search: 391 files uncommitted"). A repo's page has **Ask about these changes**: the question goes to the project's Slack channel with the list of changed files, and Claude is told to only read (`git diff`) and answer. New `staleWork`, `StaleRepo`.
- **Sessions page**: fix: chats were all titled "(no message yet)" when transcripts belong to the run user (`claude.runAs`); the first message is now read as that user (`sudo head -c 64K`, new `firstPromptOf`) and kept in memory. Faster: new indexes `runs (thread_key, started_at)` and `runs (session_id, started_at)` (the list took about 1 s for 200 sessions). Chat titles are the message's first line. A reply in a job's thread keeps the session a job (`SessionOverview.jobId`). Fix: a job session whose last turn was a learning turn showed as a chat with the learning turn's status; `sessionsOverview`'s `lastRun` now skips learning turns, and a session with a job id is a job. New: a search box (title, what happened, job id, project), day headings (Today, Yesterday, dates), the first line of what each job run did, and "● running" on sessions with a run working now.
- **Schedule is now the Jobs page's Timeline view.** The sidebar has one **Jobs** item; its pages have two views, **List** (`/jobs`) and **Timeline** (`/schedule`, same URL as before), which keep the project filter between them. A job's planned length is changed in one place, its card in List (details: **Change**, or **Use N min** when it is far off); the Timeline shows lengths as text, and each overlap links to the job to fix. `GET /schedule` and `/schedule/conflicts` are unchanged.
- **Schedule**: queues with `slots` and a job executor are drawn at their slot times as runs of that job, tagged "content queue · 2 approved" (counting the items of queues that `fills` it); a slot with nothing approved is drawn dimmed and takes no busy time and clashes with nothing. This is also in `GET /schedule` and `/schedule/conflicts`. Today has a **Now** line and "● running now" on the running job's slot (linking to its live transcript); past runs link to their transcript. "Runs often" says how often ("Every 10 min", "Hourly") instead of a capped count ("13 times"). A **Yesterday** chip shows what ran and what was missed ("no run"). Project chips with no jobs are left out. `DayPlan.often` has `everyMinutes` instead of `runs`.
- **Jobs page**: each job shows its last 7 days ("≈15% of job usage · 32 runs · $55 this week", cost at API prices), and the page head the week's total and the top 3 jobs' share; **Sort: Most usage** reorders the cards. A planned length (`durationMinutes`, which the Schedule plans with) far from what runs take (75th percentile of the scheduled runs where the model ran: the first run in each thread, so continuations after a card decision do not count; at least 3) shows "takes ~4 min (planned 45)" and a **Use 4 min** button (`POST /jobs/<p>/<id>/duration`). Jobs with no schedule (run by a queue) are folded at the bottom under "Run by a queue". Project chips with no jobs are left out. Schedules: `*/10 * * * *` reads "Every 10 min", `0 * * * *` "Hourly", `15 */2 * * *` "Every 2 hours at :15". New `jobWeeks`, `lengthOff`.
- **Queue page**: every row says when it goes out: the first batch "goes out …", the rest "~ …" from the queue's slots and batch (caps not counted). A queue that `fills` another shows "after content's 2 items" on its rows and "waits while content has 2" in its head, instead of the filled queue's next slot. Each queue's head says when it last sent something ("last out 16h ago", or "last run failed …" in red), from its done and failed items of the last 14 days. Rows approved more than 3 days ago show their age in amber, and **Other queues** opens by itself when one of its items is that old. A row's title opens the draft as approved: text, media and field values. `mediaHtml` is shared with the Approvals page; the fold arrow style moved to the shared CSS.
- **Approvals page**: Waiting is now three sections instead of a group per kind: **Needs your answer** (questions; cards a paused job run waits on first, tagged "a run is waiting", then the oldest), **Drafts to send** (queue drafts by kind, biggest first, each with Approve all) and **For your information** (`notice` cards, with **Mark all seen**). Cards are folded to their title, meta and buttons; the title opens the rest, and `#item-<id>` links (and a filter showing one or two cards) open them. Cards show the job's name instead of its id, how many checks they have, and "expires in …" in their last day (project `approvals.expireDays`). Kind chips: the six biggest, the rest under **More**, with readable names (`seo-code-change` → "SEO code change"). Notices no longer count as waiting (tab, sidebar badge, Home). Done shows "500+" at the list limit. Videos on cards load when played (`preload="none"`).
- **Live session page**: a session with a run working in it shows a live card above the transcript: a running clock, every step as it happens (sub-agent steps indented, failures in red), the end of what Claude is writing, and **Stop** (unlocked browsers on another device; ends the run as "stop" in its Slack thread would). The page polls `GET /sessions/<id>/live` every 2.5 s and reloads with the full transcript when the run ends, instead of reloading every minute. New `POST /sessions/<id>/stop`. Live tasks and Stop no longer need the Command page (`live`).
- **Home page**: recent runs open their **transcript** (`/sessions/<id>`) instead of the run record, so you can see what happened; runs with no session (the check before the run found nothing to do) still open `/runs/<id>`, which now has an **Open transcript →** button. "Just ran" lists only runs that did something, each with its reply's first line (or the error's), and folds the rest into "N more runs in the last 24 hours found nothing to do". "Running now" links each job to its live transcript (the page refreshes while it runs). "Coming up" leaves out jobs that start every 30 minutes or more often and lists them once ("Also every 10m: …"). Waiting approvals are broken down per project and kind with the oldest card's age, plus "Start with these": the three cards to decide first (ones a paused run waits on, then the oldest). New **Claude usage** stat (the CLI's latest rate-limit report, else the latest run's from the last 5 hours). Failing jobs get **See what happened**. A session page with no transcript (old, or another CLI) shows its run's reply and error. Approval cards have `id="item-<id>"` anchors. New `ServerOptions.activity`, `Store.latestSessionRun`.
- **Project tabs**: a project's own app shows inside tara-agent's dashboard. `.tara/config.json` `tabs` (`[{path, label, icon?}]`) lists its pages under the project's title in the sidebar; `/p/<name><path>` frames `/app/<name><path>`, which is proxied (behind the dashboard token, tara-agent's cookies removed, `x-tara-prefix` added) to the app's `dashboardUrl`. The address and the lit tab follow the app's own navigation. Projects with tabs leave the Dashboards switcher, and the Command page's "Dashboard ↗" opens `/p/<name>`. See docs/dashboard-look.md "Project tabs".
- `propose_item` takes `autoApprove: true`, so a run's own drafts (e.g. Reddit comments) can be auto-approved where the host `autoApprove` rule covers the kind and the project's server says yes. The tool says when the card was approved. `/internal/item` passes it on and returns the card's `status`.
- Auto-approve now also asks again when a key's first card is refreshed or revised while still pending (a person supplied the missing answer in Slack, say); a key with any decided or closed card still always waits for a person. New `Store.hasDecidedKey`.
- **Notice cards**: `POST /items/ask` with `kind: "notice"` tells instead of asks. Its first option (e.g. "Seen") just closes it with no run; any other option goes to the agent in the card's thread as usual.
- **`read_ci_job`** (host `github` projects): a read-only tara tool that reads a GitHub Actions job of the project's repo from its URL or id: workflow, branch, commit, conclusion, failed steps, the lines around the first `##[error]` and the last 300 log lines (timestamps and ANSI codes removed). Only GETs; other repos are refused; the log's signed download URL is fetched without the token, and the token never appears in output or errors. `TARA_GITHUB_TOKEN` needs **Actions: Read-only**. New `POST /internal/ci-job`. See docs/security.md "CI jobs".
- **Pull requests from a run** (host `github`: `{project, repo, base}`, token `TARA_GITHUB_TOKEN`): new tara tools `start_pull_request` (a workspace: a fresh copy of the base branch, or of the open PR's branch, in a temp folder the run can write) and `open_pull_request` (commits the workspace, pushes to `<agentName>/<name>` and opens the PR, or adds a commit to it). The token never reaches a run (`TARA_GITHUB_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN` are stripped); git runs on tara-agent's own bare repo under `<stateDir>/github/` with no config files or hooks; no force pushes, no merges; `.github/`, env, key and credential files are refused. New `POST /internal/pr-start` and `/internal/pr-open`. See docs/security.md "Pull requests".
- **Auto-approved cards** (host `autoApprove`: `{project, kind, url}`): a project server can ask for a draft card to be approved without a person (`POST /items` with `autoApprove: true`). tara-agent asks the project's `url` and approves the card as `auto` (sealed, queued, on the Approvals page and in Slack with the reason) only on `{approve: true}`, only for a key's first card and only with no checks. The rule lives in the host config so a run can't turn it on. New `Store.hasKey`. See docs/security.md "Auto-approved cards".
- **Queue `fills`** (`.tara/queues.json`): a queue can fill another queue's empty slots instead of having a schedule of its own. When a slot of the filled queue has nothing of its own due, it runs a batch of the filling queue; otherwise the filling queue waits ("Approve & run now" still runs at once). E.g. product reels in `content` go first and owner Shorts in `channel` post only on days no reel is waiting. The Queue page shows "fills empty <queue> slots", and `GET /queues` returns `fills`. A queue that fills another can't have slots or windows, and the queue it fills must have slots.
- **Security fix:** a Slack reply that continues an agy job's session now runs under that job's `agyPermissions`. It used to get no rules, so in a `bypassPermissions` project agy ran with `--dangerously-skip-permissions`. A job without rules (or one that's gone) gets only tara's tools; a thread reply never skips agy's checks.
- Cards raised by a reply in a job's thread belong to that job (`jobId`), so their decisions continue as the job (locks, timeout, `handoff`) like the run's own cards. New `Store.threadJob`.
- **Job `handoff`** (`{harness, model}`): an approved card of the run continues in a fresh session on another harness, e.g. an agy job that finds problems and leaves the approved fixes to Claude Code. The new session gets the card, the decision and the job's prompt, in the run's scratch folder; later cards come with their details; a declined card runs no model at all. Card decisions now carry the card (title, details, declined) to the job. See docs/configuration.md "Handoff".
- Fix: a job's scratch folder survives a change of session id. agy reports its own conversation id, so an agy run continued after a card decision used to get a new, empty `$TARA_SCRATCH` and lost the files the run saved. Sessions store the id their scratch folder is named after (new `sessions.scratch_id` column).
- **Job `steps` and `mcpServers`**: `steps` run one after the other before the main prompt, each in a fresh session of the job's harness (prompt from `promptFile` + `prompt`, own `timeoutMinutes`, `model` and `agyPermissions`), and their replies reach the main prompt under `## Step Output`; a failed step is marked and the next one runs. `mcpServers` adds the job's own stdio MCP servers to every session of the job, with `${VAR}` replaced from the run's environment (Claude: an extra `--mcp-config` file; agy: the per-run plugin, tools `tara_<name>`). See docs/configuration.md "Steps and MCP servers".
- **agy jobs** (`"harness": "agy"`): a job can run on Google's Antigravity CLI instead of Claude Code, with the same pre-script, Slack thread, approval cards, `send_file` and continue-after-decision. agy runs in stream-json mode with the prompt on stdin; tara's MCP server and the system prompt reach it through a per-run plugin (`--add-dir`). Job `agyPermissions` (`allow`/`deny`/`ask`) become session-only agy settings; without them a `bypassPermissions` project skips agy's checks. Host `agy.bin`. Sessions store their harness (new `sessions.harness` column) so card decisions and thread replies continue on the same CLI. The dashboard shows agy jobs as "agy (Antigravity CLI) · model". Self-improvement turns stay Claude-only. See docs/configuration.md "agy jobs".

- **`withdraw_card`**: a run can close a waiting card raised in its own thread when the person did the work themselves or it no longer applies, instead of asking them to tap a button. The card ends as cancelled with the reason (Approvals page and Slack), and cards of other threads are refused. New `POST /internal/withdraw` `{id, reason?}`; `Approvals.withdraw` takes who withdrew it.
- **Queue page** (`/queue`, its own sidebar entry): approved drafts, one section per queue in run order, with the next slot or window. Queues with the new `"reorder": true` (`.tara/queues.json`) show even when empty, with cards still to approve, and can be reordered; the rest are read-only under **Other queues**. Drag a row (mouse or touch) or use **Top**, **↑**, **↓**, **Bottom** to choose what goes out next. In a queue that alternates kinds, each kind is its own line. Items approved later still go to the end. Replaces the Approvals page's Scheduled tab (`/approvals?tab=scheduled` redirects). New `queue_rank` column on items, and `POST /items/<id>/move` `{to}` with `up`, `down`, `top`, `bottom` or a place (0 is first) (unlock cookie needed).
- **Command** (`/command`, host `live`, key `TARA_LIVE_API_KEY`): talk to tara out loud through Gemini Live, with Claude doing the work. A control room in three columns: **Systems** (every connected project's jobs, approvals, branch and uncommitted files, with buttons), the voice core with transcript and typed turns, and **Operations**, where every tool call shows up as a panel. Voice tools: `attention`, `projects`, `jobs`, `job` (run, pause, resume), `repo`, `approvals`, `decide` (only cards it has shown, after a spoken yes), `ask` (read-only `claude -p`), `dispatch` (a Slack thread), `status`, `focus`. Panel buttons (Run now, an approval's options) ask once more, then go through the same code. **Live tasks**: every Claude run (Slack chats, scheduled jobs, questions) streams onto the page with its steps, the end of its text and a Stop button (`stop` tool too); when work Command started ends, it says how it went. Step text is masked for secrets. An agent-console look: a canvas core with a waveform from the real microphone and voice, projects around it with links that pulse while work runs there, a Watch view for one task (`watch` tool), a short boot, a gauge strip, diff and run-history panels (`repo` with `file`), and optional UI sounds. **Alerts**: a new urgent item is said in one line (by the voice model while you talk, else the browser's voice, one tab only), with a chime and a red flash, at most once per `live.urgentGapMinutes`; focus mode holds them and sums them up when it ends, except `live.alwaysInterrupt` jobs. Work started from Command that ends while the voice is closed is said too. **Brief me** (button, or `brief` tool by voice). Needs the unlock cookie. `GET /attention` returns what needs you in tiers. See `docs/command.md`.
- **Photos and files in Slack**: files posted with a message (not voice clips; up to 10, 20 MB each) are downloaded to `<scratch>/slack/<ts>-<n>-<name>` and listed in the prompt for Claude to read. A message with only a photo now starts a turn too.
- Host `concurrency` defaults to 8 chat sessions at once (was 2). Hosts that set it keep their value.
- **No more `!` commands in Slack.** `!new`, `!model`, `!status`, `!jobs`, `!health` and `!run` are gone; such messages go to Claude like any other. Typing `stop` on its own (also `cancel`, `abort`, `halt`; `!stop` still works) stops whatever runs in the thread. A reply sent while a run works waits for it, and the thread says so. "run <job name>" stays.
- **Job threads hold their thread**: a reply in a running job's thread waits for the job instead of resuming the same session alongside it, and `stop` there ends the job. Chat turns and jobs share one per-thread tracker (`src/sessions/threads.ts`).
- **Code page** (`/code`, host `code`): each repo's uncommitted changes with coloured diffs, a file browser and search (file names and text, one repo or all, `?q=`), read-only and phone-friendly, plus an **Ask** box that starts a Slack thread about a file or diff (unlock cookie needed). Git runs read-only through a private index copy, so the git data can be a one-way copy from another machine (`gitDir`). Only files git lists are served; `exclude` hides `.env*` and keys. API: `GET /code`, `/code/<repo>`, `/diff`, `/file`, `/files`, `POST /code/<repo>/ask`.
- **The inbox is gone**: everything that needs a person is an approval card. `add_task`, `list_tasks`, `complete_task`, the Inbox page, `/inbox` and `tara-agent import-tasks` are removed, and the `inbox` table is dropped. `request_approval` now also covers suggestions and things only a person can do (a login, an OTP, a failure Claude could not fix), and a scheduled job finishes everything it can before it raises its cards at the end. New `POST /items/ask` lets a project server raise a card outside any run (a login that expired, a send that bounced): it is posted in the project's channel, one per pending `key`, and the decision goes to Claude in that thread.
- Queues take `slack: true`: each card is posted in the project's Slack channel (its own message, or in the thread of the run that proposed it; no buttons, decisions stay on the Approvals page). The message follows decisions and withdrawals; a Revise, the executing run and the outcome from any executor (job, URL, external progress and result) go in the card's thread. A refreshed card keeps its Slack thread.
- **Root actions** (`request_privileged`, host `privileged`): a run with no sudo can ask for an action from the allowlist of a root-owned helper (`deploy/tara-priv.mjs`, one sudoers rule for the tara-agent user). `auto` actions (e.g. re-applying permissions) run at once; others become approval cards whose approval runs the action and continues the run (chat or scheduled job) with its output. Free-form commands become "run this yourself" cards. Every root action stays on the Approvals page with exit code and output.
- Transcripts Claude wrote readable by the run user only are read as that user (sudo), so the Session page works under split users again.
- API: `GET /runs`, `GET /sessions`, `GET /sessions/<id>/transcript`, and `POST /sessions/<id>/message` (admin token) so a person's own Claude can read a run and continue its thread after a fix.

- The system prompt reaches Claude in a file (`--append-system-prompt-file`), not on the command line: under split users sudo logged the whole prompt on every run.
- Host `agentName` (default `tara`): Claude is told its name in every run, and the dashboard shows it.
- `jobs.json` takes a file-level `tz` for every job that doesn't set its own, and an optional `durationMinutes` per job for planning tools.
- **Approvals**: one card per decision or draft, from every project, on a new Approvals page. `request_approval` cards are stored (with the proposal) and can be decided on the page or in Slack; a decision on a job's card continues that run **as the job** (its locks, prompt and timeout), not as a chat turn. New `propose_item`, `list_items` and `finish_item` tools for drafts that go out later through **queues** (`.tara/queues.json`: windows per region, cron slots with alternating kinds, daily and weekly caps, gaps, batches; job or URL executors; unreported items fail instead of running twice). Edits, bulk approve, approve-and-run-now and revise on the page; project checks through `approvals.validateUrl`; a signed `approvals.hookUrl` call when an item is decided or finishes; only the first option runs a draft, the others close it (Skip, "Applied by hand"); up to 40 fields per card, with their labels in the executor's prompt; a URL executor can answer "later" to keep an item queued until a given time; `external` queues that the project's server runs itself and reports (`POST /items/<id>/report`); a cancel is told to the project's hook; a project can withdraw a waiting card (`POST /items/<id>/withdraw`) and read its queues' next slots (`GET /queues`); pending items expire. API: `/items`.
- **Split users**: host `claude.runAs` runs Claude and pre-run scripts as another OS user through sudo, so runs can't read tara-agent's database or keys. Dashboard decisions need an unlock cookie (`TARA_ADMIN_TOKEN`) and another device; approved items are sealed with `APPROVAL_SEAL_KEY`. `deploy/split-users.sh` sets it up.
- **Schedule** page and `GET /schedule`, `/schedule/conflicts`: each day's runs from the live scheduler with usual lengths, overlaps, tight gaps and free windows; `POST /jobs/<p>/<id>/duration` sets `durationMinutes`.
- Dashboard: dark only, in a shared look other dashboards can copy (`src/http/look.ts`, `docs/dashboard-look.md`); a "Dashboards" switcher from each project's `dashboardUrl` (new optional project `title`) replaces the project cards; Home shows failing and paused jobs, coming up and just ran; plain wording ("Run now" everywhere, no file names in dialogs); HTML 404 and 500 pages.
- With `TARA_HTTP_TOKEN` set, the pages need the token too (open one once with `?token=…` to sign the browser in with a cookie); before, they were served without it while the dashboard's own buttons failed.

## 0.1.0 (2026-10-25)

First release.

- **Slack threads → Claude Code sessions**: one session per thread, resumed on reply and across restarts; native streaming (live task card + text as it is written, with an edited-message fallback); `!new`, `!model`, `!stop`, `!status`, `!jobs`, `!health`; start any scheduled job by typing "run <job name>" (buttons when ambiguous, Claude's `run_job` tool for anything looser).
- **Many projects**: each Slack channel maps to a repo; Claude runs with that repo's `CLAUDE.md`, skills and `.mcp.json`.
- **Scheduled jobs** from `<repo>/.tara/jobs.json`: cron with timezones, pre-scripts with a wake gate, `[SILENT]` / `[CRON_FAILURE]`, headline + thread delivery (hand-started runs stream live into the thread), exactly-once slot claims, catch-up after downtime, named locks, hot reload.
- **Approvals, permission prompts and files** through tara's own MCP server: `request_approval` buttons that resume the session, Allow/Deny prompts for tools outside `allowedTools`, `send_file`.
- **Daily health digest** per project: runs, problems, missed slots, peak 5-hour usage.
- **Dashboard and local API** on `127.0.0.1:4100`: sessions with full transcripts, jobs with Run now, single runs; JSON for tools on the same paths; `allowFrom` network allow-list; `fallback` pass-through for taking over a port.
- A scheduled run cut short by a restart (or a crash) runs again on the next start, once.
- **`import-hermes`** to move Hermes Agent cron jobs over, and **`validate`** to check config.
- Runs as a dedicated unprivileged user (`deploy/systemd/tara-agent-dedicated-user.service`, `docs/security.md`).
