# Changelog

## Unreleased

- **Security fix:** a Slack reply that continues an agy job's session now runs under that job's `agyPermissions`. It used to get no rules, so in a `bypassPermissions` project agy ran with `--dangerously-skip-permissions`. A job without rules (or one that's gone) gets only tara's tools; a thread reply never skips agy's checks.
- Cards raised by a reply in a job's thread belong to that job (`jobId`), so their decisions continue as the job (locks, timeout, `handoff`) like the run's own cards. New `Store.threadJob`.
- **Job `handoff`** (`{harness, model}`): an approved card of the run continues in a fresh session on another harness, e.g. an agy job that finds problems and leaves the approved fixes to Claude Code. The new session gets the card, the decision and the job's prompt, in the run's scratch folder; later cards come with their details; a declined card runs no model at all. Card decisions now carry the card (title, details, declined) to the job. See docs/configuration.md "Handoff".
- Fix: a job's scratch folder survives a change of session id. agy reports its own conversation id, so an agy run continued after a card decision used to get a new, empty `$TARA_SCRATCH` and lost the files the run saved. Sessions store the id their scratch folder is named after (new `sessions.scratch_id` column).
- **Job `steps` and `mcpServers`**: `steps` run one after the other before the main prompt, each in a fresh session of the job's harness (prompt from `promptFile` + `prompt`, own `timeoutMinutes`, `model` and `agyPermissions`), and their replies reach the main prompt under `## Step Output`; a failed step is marked and the next one runs. `mcpServers` adds the job's own stdio MCP servers to every session of the job, with `${VAR}` replaced from the run's environment (Claude: an extra `--mcp-config` file; agy: the per-run plugin, tools `tara_<name>`). See docs/configuration.md "Steps and MCP servers".
- **agy jobs** (`"harness": "agy"`): a job can run on Google's Antigravity CLI instead of Claude Code, with the same pre-script, Slack thread, approval cards, `send_file` and continue-after-decision. agy runs in stream-json mode with the prompt on stdin; tara's MCP server and the system prompt reach it through a per-run plugin (`--add-dir`). Job `agyPermissions` (`allow`/`deny`/`ask`) become session-only agy settings; without them a `bypassPermissions` project skips agy's checks. Host `agy.bin`. Sessions store their harness (new `sessions.harness` column) so card decisions and thread replies continue on the same CLI. The dashboard shows agy jobs as "agy (Antigravity CLI) · model". Self-improvement turns stay Claude-only. See docs/configuration.md "agy jobs".

- **`withdraw_card`**: a run can close a waiting card raised in its own thread when the person did the work themselves or it no longer applies, instead of asking them to tap a button. The card ends as cancelled with the reason (Approvals page and Slack), and cards of other threads are refused. New `POST /internal/withdraw` `{id, reason?}`; `Approvals.withdraw` takes who withdrew it.
- **Queue page** (`/queue`, its own sidebar entry): approved drafts, one section per queue in run order, with the next slot or window. Queues with the new `"reorder": true` (`.tara/queues.json`) show even when empty, with cards still to approve, and can be reordered; the rest are read-only under **Other queues**. Drag a row (mouse or touch) or use **Top**, **↑**, **↓**, **Bottom** to choose what goes out next. In a queue that alternates kinds, each kind is its own line. Items approved later still go to the end. Replaces the Approvals page's Scheduled tab (`/approvals?tab=scheduled` redirects). New `queue_rank` column on items, and `POST /items/<id>/move` `{to}` with `up`, `down`, `top`, `bottom` or a place (0 is first) (unlock cookie needed).
- **Command** (`/command`, host `live`, key `TARA_LIVE_API_KEY`): talk to tara out loud through Gemini Live, with Claude doing the work. A control room in three columns: **Systems** (every connected project's jobs, approvals, branch and uncommitted files, with buttons), the voice core with transcript and typed turns, and **Operations**, where every tool call shows up as a panel. Voice tools: `attention`, `projects`, `jobs`, `job` (run, pause, resume), `repo`, `approvals`, `decide` (only cards it has shown, after a spoken yes), `ask` (read-only `claude -p`), `dispatch` (a Slack thread), `status`, `focus`. Panel buttons (Run now, an approval's options) ask once more, then go through the same code. **Live tasks**: every Claude run (Slack chats, scheduled jobs, questions) streams onto the page with its steps, the end of its text and a Stop button (`stop` tool too); when work Command started ends, it says how it went. Step text is masked for secrets. An agent-console look: a canvas core with a waveform from the real microphone and voice, projects around it with links that pulse while work runs there, a Watch view for one task (`watch` tool), a short boot, a gauge strip, diff and run-history panels (`repo` with `file`), and optional UI sounds. **Alerts**: a new urgent item is said in one line (by the voice model while you talk, else the browser's voice, one tab only), with a chime and a red flash, at most once per `live.urgentGapMinutes`; focus mode holds them and sums them up when it ends, except `live.alwaysInterrupt` jobs. Work started from Command that ends while the voice is closed is said too. **Brief me** (button, or `brief` tool by voice). Needs the unlock cookie. `GET /attention` returns what needs you in tiers. See `docs/command.md`.
- **Photos and files in Slack**: files posted with a message (not voice clips; up to 10, 20 MB each) are downloaded to `<scratch>/slack/<ts>-<n>-<name>` and listed in the prompt for Claude to read. A message with only a photo now starts a turn too.
- Host `concurrency` defaults to 8 chat sessions at once (was 2). Hosts that set it keep their value.
- **No more `!` commands in Slack.** `!new`, `!model`, `!status`, `!jobs`, `!health` and `!run` are gone; such messages go to Claude like any other. Typing `stop` on its own (also `cancel`, `abort`, `halt`; `!stop` still works) stops whatever runs in the thread. A reply sent while a run works waits for it, and the thread says so. "run <job name>" stays.
- **Job threads hold their thread**: a reply in a running job's thread waits for the job instead of resuming the same session alongside it, and `stop` there ends the job. Chat turns and jobs share one per-thread tracker (`src/sessions/threads.ts`).
- **Code page** (`/code`, host `code`): each repo's uncommitted changes with coloured diffs, a file browser and search (file names and text, one repo or all, `?q=`), read-only and phone-friendly, plus an **Ask** box that starts a Slack thread about a file or diff (unlock cookie needed). Git runs read-only through a private index copy, so the git data can be a one-way copy from another machine (`gitDir`). Only files git lists are served; `exclude` hides `.env*` and keys. API: `GET /code`, `/code/<repo>`, `/diff`, `/file`, `/files`, `POST /code/<repo>/ask`.
- **The inbox is gone**: everything that needs a person is an approval card. `add_task`, `list_tasks`, `complete_task`, the Inbox page, `/inbox` and `tara-agent import-tasks` are removed, and the `inbox` table is dropped. `request_approval` now also covers suggestions and things only a person can do (a login, an OTP, a failure Claude could not fix), and a scheduled job finishes everything it can before it raises its cards at the end. New `POST /items/ask` lets a project server raise a card outside any run (a login that expired, a send that bounced): it is posted in the project's channel, one per pending `key`, and the decision goes to Claude in that thread.
- Queues take `slack: true`: each card is posted in the project's Slack channel (its own message, or in the thread of the run that proposed it; no buttons, decisions stay on the Approvals page). The message follows decisions and withdrawals; a Revise, the executing run and the outcome from any executor (job, URL, external progress and result) go in the card's thread. A refreshed card keeps its Slack thread.
- **Root actions** (`request_privileged`, host `privileged`): a run with no sudo can ask for an action from the allowlist of a root-owned helper (`deploy/tara-priv.mjs`, one sudoers rule for the tara-agent user). `auto` actions (e.g. re-applying permissions) run at once; others become approval cards whose approval runs the action and continues the run (chat or scheduled job) with its output. Free-form commands become "run this yourself" cards. Every root action stays on the Approvals page with exit code and output.
- Transcripts Claude wrote readable by the run user only are read as that user (sudo), so the Session page works under split users again.
- API: `GET /runs`, `GET /sessions`, `GET /sessions/<id>/transcript`, and `POST /sessions/<id>/message` (admin token) so a person's own Claude can read a run and continue its thread after a fix.

- The system prompt reaches Claude in a file (`--append-system-prompt-file`), not on the command line: under split users sudo logged the whole prompt on every run.
- Host `agentName` (default `tara`): Claude is told its name in every run, and the dashboard shows it.
- `jobs.json` takes a file-level `tz` for every job that doesn't set its own, and an optional `durationMinutes` per job for planning tools.
- **Approvals**: one card per decision or draft, from every project, on a new Approvals page. `request_approval` cards are stored (with the proposal) and can be decided on the page or in Slack; a decision on a job's card continues that run **as the job** (its locks, prompt and timeout), not as a chat turn. New `propose_item`, `list_items` and `finish_item` tools for drafts that go out later through **queues** (`.tara/queues.json`: windows per region, cron slots with alternating kinds, daily and weekly caps, gaps, batches; job or URL executors; unreported items fail instead of running twice). Edits, bulk approve, approve-and-run-now and revise on the page; project checks through `approvals.validateUrl`; a signed `approvals.hookUrl` call when an item is decided or finishes; only the first option runs a draft, the others close it (Skip, "Applied by hand"); up to 40 fields per card, with their labels in the executor's prompt; a URL executor can answer "later" to keep an item queued until a given time; `external` queues that the project's server runs itself and reports (`POST /items/<id>/report`); a cancel is told to the project's hook; a project can withdraw a waiting card (`POST /items/<id>/withdraw`) and read its queues' next slots (`GET /queues`); pending items expire. API: `/items`.
- **Split users**: host `claude.runAs` runs Claude and pre-run scripts as another OS user through sudo, so runs can't read tara-agent's database or keys. Dashboard decisions need an unlock cookie (`TARA_ADMIN_TOKEN`) and another device; approved items are sealed with `APPROVAL_SEAL_KEY`. `deploy/split-users.sh` sets it up.
- **Schedule** page and `GET /schedule`, `/schedule/conflicts`: each day's runs from the live scheduler with usual lengths, overlaps, tight gaps and free windows; `POST /jobs/<p>/<id>/duration` sets `durationMinutes`.
- Dashboard: dark only, in a shared look other dashboards can copy (`src/http/look.ts`, `docs/dashboard-look.md`); a "Dashboards" switcher from each project's `dashboardUrl` (new optional project `title`) replaces the project cards; Home shows failing and paused jobs, coming up and just ran; plain wording ("Run now" everywhere, no file names in dialogs); HTML 404 and 500 pages.
- With `TARA_HTTP_TOKEN` set, the pages need the token too (open one once with `?token=…` to sign the browser in with a cookie); before, they were served without it while the dashboard's own buttons failed.

## 0.1.0 (2026-10-25)

First release.

- **Slack threads → Claude Code sessions**: one session per thread, resumed on reply and across restarts; native streaming (live task card + text as it is written, with an edited-message fallback); `!new`, `!model`, `!stop`, `!status`, `!jobs`, `!health`; start any scheduled job by typing "run <job name>" (buttons when ambiguous, Claude's `run_job` tool for anything looser).
- **Many projects**: each Slack channel maps to a repo; Claude runs with that repo's `CLAUDE.md`, skills and `.mcp.json`.
- **Scheduled jobs** from `<repo>/.tara/jobs.json`: cron with timezones, pre-scripts with a wake gate, `[SILENT]` / `[CRON_FAILURE]`, headline + thread delivery (hand-started runs stream live into the thread), exactly-once slot claims, catch-up after downtime, named locks, hot reload.
- **Approvals, permission prompts and files** through tara's own MCP server: `request_approval` buttons that resume the session, Allow/Deny prompts for tools outside `allowedTools`, `send_file`.
- **Daily health digest** per project: runs, problems, missed slots, peak 5-hour usage.
- **Dashboard and local API** on `127.0.0.1:4100`: sessions with full transcripts, jobs with Run now, single runs; JSON for tools on the same paths; `allowFrom` network allow-list; `fallback` pass-through for taking over a port.
- A scheduled run cut short by a restart (or a crash) runs again on the next start, once.
- **`import-hermes`** to move Hermes Agent cron jobs over, and **`validate`** to check config.
- Runs as a dedicated unprivileged user (`deploy/systemd/tara-agent-dedicated-user.service`, `docs/security.md`).
