# Changelog

## Unreleased

- **An approved card is never left half done in silence.** When the run acting on an approved card timed out or failed, the card still said `done` (it was marked done the moment it was decided) and only an unmentioned Slack line said the run stopped. Now that card turns `failed` with the reason, and a **`Not finished: <title>`** card (*Continue it* / *Skip*) goes in the run's thread: *Continue it* resumes the run's session, or a new session with the original handoff plus "check what is done, do only the rest". Every job run that times out or fails (❌) now also mentions the person who decided or the project owner in its Slack summary. `Approvals.unfinished`, `Store.failDecidedItem`, `DecidedCard.itemId`/`kind`, `raiseUnfinished` and `summarize(…, alert)` in src/scheduler/job-runner.ts; `mention` in `postSummary` no longer needs `replyIn`.
- **Vault: runs sign in to websites without seeing a password.** Saved logins (account, password, optional authenticator key) are encrypted in tara.db with `TARA_VAULT_KEY`. A run calls `vault_sign_in`, and tara-agent signs the project's Chrome in from its own tab: it fills each step (account, password, TOTP code), submits, closes the tab and tells the run only how it went. Only https pages on the login's sites; never retried after a wrong password (the login waits 30 minutes for a person); captchas and SMS/email codes still go to a person. New **Vault** page (🔐) to add, change, show and delete logins from an unlocked browser, with a log of every use; `vault_logins` tool; `GET/POST /vault`. New `src/vault/` (`crypto.ts`, `totp.ts`, `sign-in.ts`, `cdp.ts`, `vault.ts`), `src/http/vault-page.ts`, `src/http/routes/vault.ts`; docs/security.md "Vault".
- **Fix: a session's page follows its runs live again.** A reply under a dashboard run's Slack summary (and every reply typed on its page, which goes there) runs in the dashboard thread's session, but its task names the Slack thread, so the page never saw it running: no live steps, no Stop, no reload when it ended. `liveTask` (src/http/context.ts) now counts the thread's aliases. An idle session page also checks every few seconds and reloads when a turn starts (waiting while the reply box holds a draft), so a turn started from Slack or a card shows without a manual reload (`WATCH_SCRIPT` in src/http/dashboard.ts).
- **A decision's ✅ now notifies you in Slack.** When a run acts on your approval and it went fine, its result is still a reply under the job's (often days-old) Slack summary, but it now starts with a mention of the person who decided (or the project owner). Before, a reply under a bot message notified no one who didn't follow that thread, so a finished approval was silent. `mention` in `postSummary` (src/web/summary.ts), set in src/scheduler/job-runner.ts.
- **A gate's output is kept on its run.** When a job's `gate` lets the run through, what it printed (plus its exit code and error output when it failed) is saved as the run's `scriptOutput`, shown on the run page under "What the check before the run found". Before, only the model saw it, so a run's page couldn't show why it started. `gateRecord()` in src/scheduler/gate.ts.
- **Data tools for runs.** A run of a project with a `dataUrl` gets `data_tables`, `data_query` (read-only SQL), `data_rows`, `data_get`, `data_upsert` and `data_patch` from tara's MCP server. They go through tara-agent (`POST /internal/data`, `Bridge.data`), which knows the run's project: the run never sees the URL and can't reach another project's data, and the project's API applies its own table rules. Writes are logged with the project and job.
- **`packages/kit`: `http` and `runJob`** (packages/kit/README.md). The access rules two project services had copied (writes only from this machine and the tailnet, Host and same-origin checks, a person-only cookie gate) and their JSON route wrapper are now `@tara-agent/kit/http`: `tailnetOnly`, `writeGuard`, `hostAndOrigin`, `adminCookie`, `handle`, `HttpError`. Known hosts are IP literals, localhost, the machine's own hostname, `*.ts.net` and `$TARA_HOST_NAMES`. `taraClient().runJob(id, by)` starts a job now. Subpath imports (`/http`, `/tara`) skip `node:sqlite` for services on older Node types.
- **`packages/kit`: `taraClient`.** The project service's client for tara-agent (`ask`, `propose`, `jobs`, `call`, `taraThread` so cards land in the calling run's thread, `TaraError` with the status), replacing the copy each project kept.
- **`packages/kit`: shared code for project services.** `openDb` (a project's SQLite file: WAL, numbered migrations from `<repo>/.tara/db/migrations`, read-only connection, transactions) and `DataApi` + `loadTables` (the data API every project serves the same way: tables, rows, upsert, patch with `data` merge, read-only SQL, only the tables in `<repo>/.tara/db/tables.json`, `agentWritable` rules). Framework-free TypeScript, no dependencies; built from a project board's own database code. See packages/kit/README.md.
- **Data tab** (`/data`, 🗄️ in the sidebar): each project's own database through its data API (project `dataUrl`, pinnable): its tables with row counts and what they hold, the newest rows of one (50 a page), and a read-only SQL box (one SELECT/WITH, up to 1,000 rows). **Editing:** an unlocked browser (the approvals cookie) gets **Edit** on each row and **Add a row** for tables agents may write (`agentWritable`); only changed fields are sent (the API's PATCH), and the `data` JSON column as a merge patch, so a key removed in the form is removed in the row. Tables the service computes stay read-only. New `src/http/data.ts` (`dataPage`, `editPage`, `saveEdit`, `editBody`, `mergePatch`), `GET /data/<project>/edit`, `POST /data/<project>/edit`, project `dataUrl`.
- **Shared skills checked by `doctor`.** A skill vendored into several projects carries a `SHARED` file (its lines naming files of the skill, e.g. `voice-samples.md`, are per project); `doctor` warns when the other files differ between projects, so a fix made in one copy gets ported (docs/configuration.md "Shared skills"). `sharedSkills()` in src/doctor.ts.
- **Health: "Project memory" row.** Warns, quietly, when `.tara/memory.md` is over 150 lines or 12,000 characters (`MEMORY_MAX`): past that a new session never sees it. The learning note now names both limits. `oversizedMemory()` in src/memory/memory.ts.
- **Fix: a run stopped by a restart stops warning once a later run went through** (Run now, or its next slot), like gate skips before.
- **Fix: releases are readable by every user.** `tara-release` made a release read-only for others (`go-w`) but kept owner-only file modes copied from a laptop (e.g. `0600`), so a service running as its own user failed with EACCES on its `package.json`. It now also sets `a+rX`; test in test/tara-release.test.ts.
- **Fix: a gate that found nothing to do no longer shows as a missed run.** The slot keeps the run's status, so a `skipped` gate run looked like a slot skipped by a pause or a busy job, and Health and `doctor` warned "Skipped 19:15: paused, or the run before was still going". A skipped slot with its own `skipped` run is now fine.
- **No work, no model: job `gate`.** A job can name a command tara-agent runs before the model (`sh -c`, in the repo, as the run user). Exit 0 with no output, or only one line starting `Skipping` (the reason): the run ends `skipped` without a model session, and a scheduled one posts nothing (Run now says why). The gate gets the job's `timeoutMinutes`. The prompt gets the start of its output (the first 128,000 characters, then a line saying how much was cut), not the end: a briefing leads with what matters. Otherwise the run starts with the output in its prompt (`## Gate output`), so the skill works from it instead of running the check itself. This brings back the old `preScript` gate (removed when job instructions moved into skills) as an option on the job; the instructions stay in the skill. New `src/scheduler/gate.ts` (`gateRunner`, `gateSaysSkip`, `gateSection`), job `gate`, run status `skipped` (shown as "nothing to do").
- **Preflight: job `requires`.** URLs that must answer before a run starts (a browser's DevTools, a project server's `/health`). When one doesn't, the run ends `blocked` without a model session, Slack hears once per streak, and a queue's items go back to wait 15 minutes instead of failing. `blocked` counts as a failure on the Jobs and Health pages. New `missingServices`, `serviceUp`, run status `blocked`.
- **Runaway guard: job `budgetUsd`.** Passed to Claude as `--max-budget-usd`; a run the CLI stops there ends `over-budget` (💸). Unset by default: not a quota. `RunStatus` and `JobStatus` gain `over-budget` (the CLI's `error_max_budget_usd` result).
- **Never send twice: `uncertain` items.** A queue item whose run started but never said how it went (a restart mid-send, a run that ended without reporting it) used to be marked `failed`, which reads as "it didn't go out" when it may have. It is now `uncertain`: never run again on its own, listed first on the Approvals page under **Did these go out?** and on Home, with **It went out** (done), **It didn't: send again** (back in its queue) and **Drop it** (failed). New item status `uncertain`, `Store.markUncertain` / `resolveUncertain`, `Approvals.resolve`, `POST /items/<id>/resolve` `{outcome: "sent" | "retry" | "drop"}` (unlock cookie needed). An item whose executor job doesn't exist still fails: nothing ran.
- **`tara-agent doctor`.** One check of everything from a terminal: the config, every enabled job's skill and its `## Job` section, the services jobs `require`, and the running tara-agent's Health checks (`GET /health/checks`), red first. Exits 1 when anything is red. New `src/doctor.ts`.
- **Host tools** (docs/host.md, docs/deploy.md, docs/backups.md): `deploy/backup/tara-backup.mjs` (nightly, checked, age-encrypted off-site backup + `restore-test.sh`, Health checks **Off-site backup** and **Restore test** from host `backup.offsite`), `deploy/release/` (`tara-release` on the host, `tara-deploy` on your machine: release folders, automatic rollback, `.tara/deploy.json` per repo), `deploy/host/tara-heartbeat.mjs` and `tara-cleanup.mjs` with their timers, `deploy/systemd/claude-remote@.service` (Remote Control as the run user), and the desk widget's "agent is not answering" alert.

- **Startup and shutdown are tested.** `serve()` moved from `src/index.ts` into `startAgent()` in the new `src/agent.ts`, which takes the Slack gateway and the environment as options and returns `{store, http, stop}`; `index.ts` keeps the CLI, the signal handlers and `process.exit`. `stop()` now also clears the housekeeping timers (reminders, samples, scratch sweep, prune, backup, tab sweep), and the 8-second exit cap covers Slack's disconnect too. New `test/agent.test.ts` starts the whole agent from a host config with a fake Slack and a stand-in `claude`, checks `/health`, `/jobs`, `/drain` and every dashboard page, then stops it and checks Slack and the port are closed.
- **`src/http/server.ts` split into route tables** (no change in behaviour). The 2,100-line file had one closure routing every request through a chain of `if`s, and looked a project up by name about 17 times. Now `server.ts` (~500 lines) is the front door only (networks, tokens, cookies, proxies, listeners), and each area has its own table of `route('POST /items/:id/decide', …)` entries in `src/http/routes/` (`system`, `jobs`, `sessions`, `items`, `reminders`, `code`, `internal`, `pages`), with its paths listed at the top. Shared lookups (`project(name)`, `knownProject`, `dayPlan`, `human`, `transcript`, …) live in `src/http/context.ts`, the matcher in `src/http/router.ts`, request helpers in `src/http/io.ts`, the proxy in `src/http/proxy.ts`. New `test/http-routes.test.ts` covers the routes no test reached (every `/internal/*` call, job duration, schedule conflicts, bulk decide, withdraw); it passes against the old and the new server.
- **A crash no longer loses chat messages.** A message waiting behind a running turn (or for a chat slot) lived only in memory, so a crash dropped it silently. Every chat message is now kept in the store from arrival until its turn ends (`inbox` table, migration; `Store.addInbox`/`startInbox`/`removeInbox`). At start, `SessionManager.recover` answers each one that was still waiting ("↩️ Picking up your message …"), and tells the thread about one whose turn had started (not run again: it may have half done something), one older than 6 h or one whose files are gone (asks to send it again).

Skills had become logs of dated incidents ("(<name>, <date>): …"): one busy skill went from 57k to 132k characters in 12 days, read whole by every run. The learning prompt now says to edit the rule in place, write timeless instructions without dates or names (git keeps them), say each rule once, move detail some runs need to `references/<topic>.md`, keep SKILL.md under 25,000 characters (`SKILL_MAX_CHARS`, `SKILL_EDIT_RULES`) and stop bumping versions. Relative links (`references/x.md`, `../README.md#setup`, `/docs/`) open in the Code page and never leave the repo (`codeLink`); everything is escaped, so raw HTML in a file shows as text. `#L12` links and search hits go to Source. `inline` (dashboard.ts) takes an optional link resolver. Diffs stay raw.

- **Cards advise a new session or the same one, and you can override it** (docs/configuration.md "Where a decision is acted on"). Before, a card with handoff notes always started a fresh session in a new thread, even for a quick follow-up on a small run. Runs now record their context size (`context` stream event, `RunOutcome.contextTokens`, `runs.context_tokens`); the decision records the mode used (`items.session_mode`). Migration.

- **Batch 3 of the 2026-11-22 review: fairness and loose ends.** (1) **Locks before a job slot**: a job waiting for a busy browser (`chrome`) no longer holds one of the `jobConcurrency` slots meanwhile; a slot holder never waits for a lock. (2) **Waiting runs can be called off**: `Semaphore.acquire` and `Locks.acquire` take an `AbortSignal`; Pause cancels a run of that job still waiting in line (it doesn't start; queue items it carried go back as approved, `runQueue` → `not-started`), and so does a shutdown. New job `maxWaitMinutes`: a scheduled run that waited longer is skipped instead of starting late. (3) **One time limit per run**: new job `runTimeoutMinutes` (default twice `timeoutMinutes` for a job with steps): steps and the main session share it, a step with no time left is skipped and marked, the main session always gets 5 minutes to report. **Learning turns run after the job's slot and locks are given back.** (4) **`selfImprove: "trouble"` means trouble**: tool errors count only at 5 or more and at least a quarter of the run's calls (`TOOL_ERROR_TROUBLE`, `TOOL_ERROR_SHARE`); before, any 2 failed calls (a `grep` with no match) made nearly every run a learning run. (5) **Approve with edits**: the proposer's checks (a ⛔ "recipient opted out") stay when a person edits a field, only the fields' own checks are redone; and edits are refused when a run re-proposed the card while the checks ran. (6) **Loose ends**: `KeyedQueue` forgot no key (it compared the wrong promise), so it grew with every thread; `/health` shows `build` (`dist/build.json` from `scripts/after-build.mjs`, which also removes compiled files whose source is gone); a **Database** check on the Health page writes a row (`heartbeat` table, migration) and turns red when writes fail. (7) **Project tabs ask the dashboard** (`tara:decide` with a confirm, `tara:navigate`; see docs/dashboard-look.md). (8) **Tests** for the MCP server over stdio, `Incidents`, the `validate` command, and the request guards moved to `src/http/guards.ts`.
- **Batch 2 of the 2026-11-22 review.** (1) **Usage limits hold, then retry** (`src/scheduler/limits.ts`): a run that hits a limit sets a host-wide hold on its CLI until the reset (the rejected window's `resetsAt`, else the time in the CLI's message such as "resets Nov 22, 3:30pm (Asia/Kolkata)", else an hour). While held, scheduled slots start nothing and are kept as `held` (Health: "Held at …"), queue executors on it don't start (`enabled` is false) and a queue run that never got going gives its items back (`runQueue` → `held`, items deferred, not failed). When the hold ends, the latest held or limited slot of each job (under a day old) runs once (`Scheduler.retryHeld`, `Store.latestClaim`, `claimSlot(…, alsoRetake)`). A chat that hits the limit sets the hold too (`JobControl.noteLimit`), and its reset time is shown in the host timezone. `/health` lists `limits`. (2) **Safe deploys**: `POST /drain` (needs `x-tara-admin`) stops starting scheduled and queue runs (their slots are left `aborted` for the restarted process) and lets running work finish; `/health` gets `idle` (no CLI process of any kind, incl. learning turns, no job running or waiting, no queue batch), `draining` and `liveRuns`. Queue items still waiting for their executor's run when tara-agent stops go back to approved at the next start instead of failing (`items.run_started_at`, migration; `markRunStarted`, `restoreUnstarted`). (3) **Project apps on their own origin** (host `http.appPort`, `tls.appPort`; off by default): `/app/<name>/…` is served only there, a write from it to tara-agent is refused as cross-site, and the tab page follows the app's address by `postMessage` from a script the proxy adds to its HTML pages. An app asks the tab page to open a dashboard page (`tara:navigate`) or to decide one of its project's cards (`tara:decide`: the page checks the card and option, asks the person to confirm, decides, answers `tara:decided`); on by default for apps on the same origin too. (4) **Pinned project settings** (host `trusted`, keyed by repo path): `slackChannel`, `owner`, `permissionMode`, `billing`, `systemPromptFile`, `dashboardUrl`, `healthUrl`, `keepTabsUrl`, `approvals`, `reminders` come from the host config only for a listed project, and its queues may send only to `executorUrls`; differences in the repo are shown on the Health page (**Pinned settings**). (5) **The unlock cookie holds a key derived from `TARA_ADMIN_TOKEN`** (`adminCookieValue`), not the token; a browser still holding the token gets the derived key on its next page. (6) **`deploy/pull-backups.sh`** copies the daily backups to another machine over ssh (`sudo -n rsync` on the host, 30 days kept locally).
- **Safety fixes from a code review (2026-11-22).** (1) **Pause, Resume and the duration edit work for `{"skill": …}` jobs**: `editJob` looked for an `id` key, which skill jobs don't have, so all of them returned 404. (2) **A job's slot closes when its run is recorded**, before its learning turns (`runJob` `onDone`): a crash or power cut during a learning turn left the slot `running`, and catch-up ran the finished job again (a post could go out twice). (3) **`PRAGMA synchronous = FULL`** (was `NORMAL` since the 2026-11-20 disk incident): in WAL mode NORMAL drops the last commits on a power cut, so an item marked `running` before its send, or a claimed slot, could come back and run again. (4) **Auto-approve can't approve a key twice**: two proposals of one key arriving together both passed the "never decided" check before their awaits; it is asked again right before approving. Decided keys are kept in a new `decided_keys` table (migration, filled by a trigger) that retention never prunes, so a key whose card was deleted after 60 days isn't new again. (5) **`systemPromptFile` must be a file inside the repo** (realpath): a run could point it at `/proc/self/environ` and get tara-agent's secrets into its prompt at the next restart. (6) **Host check when bound beyond localhost** (`trustedHost`, new host `http.hosts`): IP addresses, `localhost`, one-word names, `*.ts.net` and the `dashboardUrl` host pass; any other name is refused, so a DNS-rebinding page can't reach the API. (7) **One bad `.tara/config.json` no longer stops every project**: that project is left out and shown on the Health page (`loadProjects(host, onBroken)`, **Projects** check); `validate` still fails on it. (8) **Refuses a database from a newer build** instead of quietly running on an unknown schema. (9) **Daily database backups** (`src/store/backup.ts`, host `backup.dir`/`backup.keep`, default `<stateDir>/backups`, 7 days): `VACUUM INTO` a temp file, `quick_check` it, then rename; hourly check so a day is never missed; **Database backup** check on the Health page. (10) **Chat summaries say how many cards wait**, as job summaries do (`ManagerDeps.approvalsUrl`): since approval cards stopped being copied to Slack, a card raised by a reminder task, a card decision or a dashboard chat went unnoticed, and a turn with an empty reply posted nothing.
